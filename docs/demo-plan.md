# AI搜答案策略共建平台 · Demo 实施计划（v3.1）

> 纯前端可交互 Demo，用于产培 Demo Day 与面试官交流。
> **v3.1 修订要点**（Manus 终审）：
> - 明确**首批用户与任务**；商业化、社区治理改为后续协作方。
> - 商业冲突移出主线，作为追问备用，并且改为"提示 + 待讨论"，不再一键采纳。
> - 评测降级为「**策略覆盖与回归检查（概念原型）**」，回归以单条样例完整追踪。
> - 复用价值锚定在**已有能力**上，新组件只作为"待研发扩展点"。
> - 补充平台边界展示和 4 张问答卡。

**Goal：** 在 5 分钟内让面试官记住一个主张：**业务改了 AI 搜的答案策略后，能检查改变了什么、有没有带来回归、哪些能力能带到别的场景。**

**Architecture：** 规则模拟引擎写成纯函数：生效配置及其来源、护栏冲突检测、答案渲染、样例覆盖与回归检查、复用清单。全部基于本地 mock 数据计算。UI 包括平台控制台和手机端 AI 搜卡片预览，两者共用一份全局状态。

**Tech Stack：** Vite + React 18 + TypeScript + Tailwind CSS + Zustand + lucide-react + Vitest（只测引擎）。图表用手写 SVG。部署可选 Vercel 静态托管。

## 1. 方案定位

> **AI搜答案策略共建平台**：让业务团队基于可复用的模板，在**不改召回和模型**的前提下，配置 AI 搜的答案策略（内容依据、答案呈现、护栏规则），检查每条结论的来源，并检查改动对固定样例的影响。

### 首批用户与任务（v3.1 新增）
- **首批用户：** 搜索/点点的**场景 PM**，以及**行业运营**。
- **他们要完成的工作：** 在不改召回和模型的前提下，配置一个场景的答案呈现策略；确认每条结论有来源；在固定样例上检查改动的影响、发现回归；为新场景复用已有能力。
- **后续协作方：** 商业化、社区治理、电商。平台为他们预留"规则来源与负责人"和冲突提示机制（Demo 里作为追问备用），**具体的协作流程以真实组织机制为准**。

### 平台边界（Demo 里要展示出来）
| 业务可配置（策略位） | 需研发/算法（平台不开放） |
|---|---|
| 内容依据：来源类型、时效窗口、亲身经验优先、商业内容标注 | 召回、排序、模型选择与调优 |
| 答案呈现：已有组件的开关和顺序、分组维度、生效范围（问题类型） | 新的答案组件、新的数据源接入 |
| 样例集：增删样例、标注期望要点（需场景负责人复核） | 语义级评测（LLM 评审 + 人工评审） |

**准入标准：** 一项能力只有在 ≥2 个场景反复需要、而且可以参数化时，才从"研发实现"沉淀为"策略位"。

### 痛点：判断 → 依据 → 待验证

| | 内容 |
|---|---|
| **已有依据（用户侧）** | 8 位访谈用户和 10 条反馈反复提到来源、时效、分歧、软广、"是否适合我"、答案太长；用户搜海参蒸蛋这类问题本来就要看真人经验（我的个人经历） |
| **产品假设（平台侧）** | 多个场景在"内容依据、答案结构、样例检查"上存在共性；策略调整依赖研发；业务团队的行业经验难以直接作用到答案上 |
| **外部旁证** | 公开报道的组织动向（见 `docs/context-for-review.md`）只说明多个团队**可能**关注 AI 搜，**不作为平台需求成立的证据** |
| **待验证** | 访谈首批用户（场景 PM、行业运营）各 2 到 3 人，后续协作方各 1 人；盘点：① 各场景策略和模板的硬编码量与重复率；② 一次策略变更从提出到上线的周期和研发占比；③ 跨团队需求的响应方式 |
| **止损判断** | 如果验证结果显示只是单一业务的偶发需求，**就不先建平台**，改为在点点内部做组件化 |

**路演口径：** "这是基于用户痛点提出、内部流程还待验证的平台方案。"语气要有判断，但不把假设说成事实。

## 3. Demo 范围

| 优先级 | 模块 | 说明 |
|---|---|---|
| **P0** | 布局框架 | 顶栏有场景切换和当前身份（默认"行业运营 · 护肤"）；左侧导航 |
| **P0** | 策略配置页 + 手机预览 | 三个页签：**内容依据** / **答案呈现** / **护栏规则**（示例规则，只读并标明负责团队）；每个策略项显示设置者；改动后预览实时变化，变化区域高亮；页面底部有一个灰色折叠区「需研发/算法（不在此配置）」，用来展示平台边界 |
| **P0** | 前后对比 | 预览区可以切换"改动前 / 改动后"，或者左右并排 |
| **P0** | 溯源面板 | 点击结论，展示原文片段、发布时间、内容类型、正反面计数。页面注明"**溯源保障的是可追溯、有依据，不代表平台为帖子的真实性背书**" |
| **P0** | 策略覆盖与回归检查（概念原型） | 8 个护肤样例，每个都有独立标注的期望要点；对比改动前后的**要点覆盖、引用可追溯、陈旧引用、商业内容是否标注**。**回归用单条样例完整追踪**：问题 → 期望要点 → 改动前输出 → 改动后输出 → 漏掉的要点 → 原因（规则生效范围过宽）→ 收窄范围后重跑。页面标注："规则模拟原型，用于检查策略改动对样例的影响，不代表语义判断准确率" |
| **P0** | 第二场景复用 | 从护肤模板新建家常菜场景 → **三栏清单**：直接复用 / 改配置 / 待研发扩展点 → 预览「海参蒸蛋」，**主体全部由已有组件拼成**；待研发组件用虚线框表示，标注"概念预览，非平台已有能力" |
| **P1（追问备用）** | 跨团队护栏冲突 | 切换为商业化身份，把「品牌说」放到结论之前 → **提示冲突**，并标明规则来源（示例规则 · 社区治理配置）和负责人 → 展示**待讨论的选项**（A 放在结论之后的明牌专区 / B 改为相关商品入口）→ 操作是「通知规则负责人并发起讨论」，**不自动采纳** |
| **P1** | 反馈治理（单页） | 只处理被反馈的帖子：AI 打标（高/中/低 + 证据条数）→ 先处理这一条引用，生成待审核变更，可撤销；证据积累到阈值后才提示可以升级 |
| **P2** | 开场叙事页 | 用户原声 → 判断/依据/待验证 → 平台定位 |
| **路线图（只口述）** | 例外审批、分层治理、语义级评测（LLM 评审 + 人工）、灰度发布与回滚、趋势雷达 | — |

**明确不做：** 登录、后端、真实 LLM、权限系统、可拖拽画布、多垂类铺量、任何线上收益数值、"答案质量评测"之类的说法。

## 4. 演示主线（5 分钟：讲 4.5 分钟，留出对话时间）

| 时间 | 步骤 | 内容 |
|---|---|---|
| **30 秒** | 定位 | 我自己搜海参蒸蛋从来不问通用 AI → 小红书 AI 搜的差异化在于组织好真人经验 → 这套"组织方式"需要由业务团队持续调整和验证 → 所以做一个平台。首批用户是场景 PM 和行业运营 |
| **90 秒** | ① 配置一项策略 + 看依据 | 以行业运营身份，在「护肤 → 选购怎么选」开启「按肤质分组」和「踩坑提醒」→ 预览前后对比：一句话结论、油皮/干皮分组、踩坑条（"3 人反馈和粉底一起用会搓泥"）→ 点开这条结论看 3 条原文。顺带指一下：每个策略项都标着设置者；页面底部写明哪些不在这里配置（平台边界） |
| **90 秒** | ② 发现并修正回归 | 跑 8 个样例 → 先看那 1 条回归样例的完整链路：「防晒和粉底的先后顺序」→ 期望要点包括"等待成膜"→ 改动后被按肤质分组拆散，漏掉了这一点 → 原因是分组规则对"用法类"问题也生效了 → 把生效范围收窄到"选购类" → 重跑，回归消失。强调：**这是规则模拟原型，期望要点独立标注；语义级评测和线上效果在路线图里** |
| **60 秒** | ③ 复用到新场景 + 总结 | 从护肤模板新建「家常菜 → 做法步骤」→ 三栏清单 → 预览「海参蒸蛋」，主体由已有组件拼成（结论条、按器具分组、翻车提醒、来源底栏、溯源），参数分布条以虚线标为待研发 → 总结：**改了什么看得见、有没有回归查得到、哪些能力能带走说得清** |

**追问备用：** 商业冲突（P1）、反馈治理（P1）、分层治理和路线图（口述）。

## 5. 指标口径

| 层级 | 指标 | Demo 中如何呈现 |
|---|---|---|
| **采用与效率**（待上线后统计，需先和业务确认基线） | 经过平台验证的策略变更数和占比；复用已有能力的场景数；策略需求从提出到完成可验证改动的周期 | 只展示复用清单中的复用占比，其余标注"待验证" |

| **线上结果**（待灰度验证） | 满意度/点踩率、改写重搜率、原文点击率 | 只列指标名和实验设计，**不显示数值** |

### 样例集的最小运营机制（口述 + 页面上一行说明）
- 由**场景负责人**维护；改动人不能单独判定"通过"。
- 样例覆盖典型场景和边界场景，按版本记录。
- 上线前按固定样例集回归；线上发现的问题补进样例集。
- 具体责任人"待与业务确认"。

### 核心类型

```ts
type Role = 'dots_pm' | 'industry_ops' | 'ads' | 'community';
type Tab = 'evidence' | 'presentation' | 'guardrail';
type QueryCategory = '选购' | '用法' | '做法' | '踩坑';

interface Scene { id: string; vertical: string; intent: string; sampleQuery: string; templateId?: string }

interface StrategyItem { id: string; sceneId: string; tab: Tab; key: string; label: string;
  value: boolean | number | string | string[];
  appliesTo?: QueryCategory[];
  setBy: { role: Role; team: string; name: string; at: string };
  isExampleGuardrail?: boolean;
  editableBy: Role[] }

interface Conflict { itemKey: string;
  guardrail: { label: string; ownerTeam: string; ownerName: string; isExample: true };
  message: string;
  options: { id: string; label: string; note: string }[];   // 待讨论，不自动采纳
  action: 'notify_owner' }

interface Post { id: string; kind: 'note' | 'comment'; parentId?: string;
  author: string; authorType: '素人' | '博主' | '合作'; date: string;
  persona?: string; stance: '推荐' | '不推荐' | '踩坑' | '中立';
  firstHand: boolean; text: string; likes: number; points: string[] }

interface AnswerModel { conclusion: string;
  sections: { id: string; component: string; title: string; planned?: boolean;
    items: { text: string; evidence: string[]; count?: number; point?: string }[] }[];
  footer: { notes: number; comments: number; sponsoredLabeled: number; latest: string } }

interface Sample { id: string; query: string; category: QueryCategory;
  expectedPoints: { key: string; label: string }[];          // 独立标注
  annotatedBy: string }                                      // 演示里写"场景负责人复核"

interface SampleCheck { sampleId: string;
  before: { answer: AnswerModel; covered: string[] };
  after:  { answer: AnswerModel; covered: string[] };
  missedAfter: string[]; traceableRate: number; staleCount: number; sponsoredUnlabeled: number;
  delta: 'improved' | 'same' | 'regressed'; reason?: string }

interface ComponentDef { id: string; name: string; status: 'existing' | 'planned'; usedBy: string[] }

interface ReuseReport {
  reusedAsIs: { name: string; kind: 'capability' | 'component' }[];
  reconfigured: { key: string; from: string; to: string }[];
  plannedExtensions: { name: string; reason: string }[];    // 待研发扩展点，不计入复用收益
  reuseShare: number }

interface FeedbackItem { id: string; postId: string; source: '点踩' | '举报' | '评论纠正';
  aiTag: { tag: '疑似软广' | '已过时' | '信息错误' | '人群错配'; level: '高' | '中' | '低'; evidence: string[] };
  action?: { scope: 'single_citation' | 'author_cluster'; status: 'pending' | 'applied' | 'reverted' };
  clusterEvidenceCount: number; clusterThreshold: number }
```

**规则模拟逻辑（要如实讲）：** 答案里出现的要点等于"被引用帖子的 points"与"已开启组件能承载的要点"的交集，再按生效范围过滤。覆盖情况通过和独立标注的 `expectedPoints` 对比得出。分组规则作用在"用法类"问题上时，会把步骤类要点拆散并截断，从而产生那条回归。**这是规则模拟器，验证的是策略改动对样例的影响，不是语义质量。**

## 8. 问答卡（彩排用）

| 追问 | 回答方向 |
|---|---|
| 内部真的需要这个平台吗？第一用户是谁？ | 首批用户是场景 PM 和行业运营，任务是在不改召回和模型的前提下配置并检查答案策略。平台需求是基于用户痛点提出的假设，验证路径是访谈加盘点；如果只是单一业务的偶发需求，就不先建平台 |
| 平台边界在哪？哪些能由业务改，哪些要改代码？ | 策略位：内容组织、已有组件开关、分组维度、生效范围、样例集。需研发/算法：召回、排序、模型、新组件、新数据源。准入标准：≥2 个场景反复需要并且可以参数化 |
| 为什么不直接让研发写死？ | 单场景、低频变更时，写死更便宜；平台成立的前提是多场景反复需要相似的策略，而且变更受研发排期卡住 |
| 为什么不是 Agent Builder？ | 不让业务自由编排模型和流程，而是把反复出现的答案策略和检查方式沉淀成受约束的能力。如果实际需求只是调 prompt，设计要相应调整 |
| 这个检查不还是你手工编码出来的必然结果吗？ | 是的，它是规则模拟原型，验证的是"策略改动对样例要点、引用、规则的影响"，不是语义准确率。真实产品要接入 LLM 评审加人工评审，放在路线图里 |
| 样例集谁维护？怎么防止只对演示题优化？ | 场景负责人维护，改动人不能单独判定通过；覆盖典型和边界场景，按版本记录；线上问题持续补进样例集；具体责任人待和业务确认 |
| 引用是对的，但原帖本身不真实怎么办？ | 平台保障的是可追溯、有依据，不为帖子的真实性背书；内容质量和来源可信度要靠治理策略（比如反馈治理）加线上验证 |
| 业务改坏了怎么办？ | 固定样例回归、版本回滚；低风险改动快速验证，高风险改动审核，审核边界尊重真实流程 |
| 检查结果变好了，但业务不用怎么办？ | 采用本身就是核心指标：经过平台验证的变更数和占比、复用已有能力的场景数。先和业务确认基线，不预先宣称效率提升 |
| 商业内容怎么办？ | 不预设商业和真实性二选一。平台只负责提示冲突、标明规则来源和负责人，选项交给责任团队按现行机制讨论（可演示 P1） |
| 第二个场景真的不用研发吗？ | 不是。主体由已有组件拼成，参数分布条是待研发扩展点，不计入复用收益，也不据此宣称多场景复用收益 |

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 主线被流程淹没 | 严格按 30/90/90/60 秒；冲突和反馈治理只在被追问时打开 |
| 被认为是在虚构组织机制 | 分层治理只口述，并说明"以真实组织为准"；冲突只提示、不裁决 |
| 被认为在包装 benchmark | 统一用"策略覆盖与回归检查（概念原型）"这个名字；页面和讲稿都说明"规则模拟" |
| 复用被认为是靠新组件撑起来的 | 预览主体只用 existing 组件；planned 组件用虚线标出，不计入复用占比 |
| 页面太满 | 每个页签最多 5 到 6 项；演示用到的放在第一位；预览变化区域高亮 |
| 现场设备或网络问题 | Vercel 部署 + 本地 `npm run preview` + 录屏 |
| 品牌问题 | 标题写"概念 Demo"；品牌名和用户名全部虚构 |
